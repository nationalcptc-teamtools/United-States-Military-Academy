## Problem, baseline and evidence

The team needs an actionable open-source tooling selection for CPTC, with strong industrial/agricultural flexibility and eventual public-repository integration. Currently there is no curated farm-focused package in this local workspace. The desired result is a prioritized catalog and a reproducible offline Kali/Linux kit with Windows enumeration tools, selected against actual evidence as it arrives.

Only **Butter Family Farms** is known about the customer's operating environment. Irrigation, grain handling, livestock facilities, greenhouses, refrigeration, telemetry, vehicles and site energy are scenario hypotheses, not established assets. The prior vendor-assessment record establishes no asset inventory or customer approval and must not be used to invent either.

## Scope, boundaries and assumptions

The initial Analyst scope delivered `proposal.md`, this specification and `tool-catalog.md`. On 2026-10-15 the user requested the remaining roles; the implementation addendum below records that progression. Neither role assignment authorizes target scans, exploitation, physical/radio operations or publication.

| ID | Reversible assumption / boundary |
| --- | --- |
| A-FT-01 | Kali/Linux is the primary preparation/runtime target; Windows tools are selected payloads for separately authorized Windows hosts. Exact OS releases, CPU architectures, .NET and privileges remain unknown. macOS support is optional. |
| A-FT-02 | Offline means tools operate without Internet after acquisition through an approved route. It does not mean no traffic to an explicitly authorized lab/target. Full dependency acquisition and staging feasibility need design. |
| A-FT-03 | Breadth is evaluated by protocol/scenario coverage, not by installing every candidate. The initial 40 entries may be reduced with recorded reasons and gaps. Alternate libraries are not all mandatory dependencies. |
| A-FT-04 | Catalog/manifests/runbooks and small team-owned helpers are likely useful commits. Vendored sources, binaries, package caches or container images are choices for Architect and eligible maintainer; no approach is preselected or approved. |
| A-FT-05 | Use the October 2025 rulebook as requested. Event-specific SOW/ROE and written clarifications control actual use. October 2025 is not assumed to be a future event date. |
| A-FT-06 | Use synthetic captures, identities, controller registers and logs for preparation. Keep actual engagement evidence in approved private event storage. Publication suitability of planning documents requires separate inspection. |

Excluded from the first operational profile: PLC logic upload/download, controller start/stop/reset, setpoint/coil/register writes, firmware changes, fieldbus replay/injection, forced outputs, RF transmission, credential spraying/brute force, persistence, denial of service and uncontrolled fuzzing. Tools possessing these features may be cataloged; their inclusion does not enable these uses. Ordinary IT testing remains conditional on scope and tool-specific approval. No customer-name-based Internet reconnaissance or searches for real farms are part of this proposal.

## Functional requirements and observable acceptance

These criteria define the later deliverable. The present Analyst documents satisfy the analysis handoff, not all kit acceptance criteria.

| ID | Required outcome | Observable acceptance criterion |
| --- | --- | --- |
| FR-FT-001 | Maintain a useful, prioritized catalog | Every `TOOL-001` through `TOOL-040` has a recorded selected/conditional/lab/hold/excluded disposition and reason. LinPEAS and WinPEAS are present by name. Selected tools are distinguished from research candidates and alternatives. |
| FR-FT-002 | Make entries actionable and attributable | Each selected tool records canonical upstream, purpose, protocol/scenario, license source and status, runtime/architecture, dependency/privilege/hardware needs, operation class, output types, limits, maintainer, checked date and smoke-check reference. Unknowns remain explicit; there are no invented pins, approvals or compatibility claims. |
| FR-FT-003 | Cover flexible primary OT interfaces | A matrix maps Modbus TCP/RTU, Siemens S7, EtherNet/IP CIP, OPC UA, BACnet/IP, MQTT and passive packet inspection to at least one candidate each. Serial-only variants name adapter constraints. Protocol/vendor coverage is supported by upstream evidence and is never inferred from a port alone. |
| FR-FT-004 | Cover agriculture-specific possibilities without inventing scope | Explicitly address CAN/J1939/ISOBUS, CANopen, LoRaWAN, Zigbee, MAVLink, DNP3, IEC 60870-5-104, IEC 61850 and DLMS/COSEM as conditional coverage, lab-only options or documented gaps. | FR-FT-005 | Support Linux and Windows host assessment | A synthetic Linux and Windows evaluation path exists for selected host-enumeration tools. | FR-FT-007 | Separate preparation from operational behavior | Acquisition/installation performs no discovery or target activity. Default checks use local synthetic files or an isolated lab. | FR-FT-008 | Provide bounded OT runbooks | Selected active operations state exact request type, possible side effects, request/connection budget, timeout, retry policy, destination/unit/address range, required credentials, stop conditions, evidence fields and cleanup. | FR-FT-010 | Exercise representative lab paths | Rehearsal demonstrates offline PCAP interpretation plus a controlled read/query for each selected primary protocol family using synthetic fixtures/simulators. | FR-FT-011 | Prepare reviewable repository integration | A later integration plan records fresh repository revision/conventions, eligible student owner, license notices, selected artifact locations and ignored private outputs. ## Relevant failure cases

| Case | Required handling / acceptance link |
| --- | --- |
| Customer technology differs from scenario hypotheses | Do not install/select based solely on the company name; update the coverage/disposition matrix against authorized evidence (FR-FT-003/004, NFR-FT-001). |
| Unsupported vendor model, encryption, OPC UA trust/auth failure, wrong Modbus unit/address/word order | Preserve error/uncertainty; no bypass, blind address sweep, guessed engineering units or automatic write. Document vendor/model limits (FR-FT-002/008/009). |
| Controller latency, dropped process traffic, unexpected output change | Stop, retain minimal evidence and follow authorized incident routing; do not retry indefinitely (FR-FT-008, NFR-FT-004). |
| Windows AV quarantine, missing .NET, insufficient shell rights, absent capture privilege | Explain prerequisite/failure; do not disable endpoint controls or infer a clean system (FR-FT-005/009). |
| Broken URL, hash mismatch, missing wheels/native library, unavailable container runtime | Fail before execution or mark unstageable. Never fetch an unpinned replacement or silently enable Internet (FR-FT-006, NFR-FT-003). |
| Tool update changes API, license or behavior | Keep the prior reviewed selection; evaluate the new release with provenance/compatibility checks. PyModbus API changes and python-snap7 runtime differences make this concrete (FR-FT-006, NFR-FT-002/006). |
| Partial/invalid XML or nonzero scanner exit in legacy wrapper | Do not treat cached hosts or generated report as a valid complete scan. Legacy remediation is separate work if reused (E-FT-06, FR-FT-009/011). |
| No CAN/RF hardware or no authorized physical access | Offline log analysis may proceed with synthetic data; hardware paths remain not run (FR-FT-004/010). |
| License conflict, public repository unavailable, event freeze already begun | Hold affected staging/publication, preserve the reviewable local plan and identify the eligible decision owner (FR-FT-011/012, NFR-FT-002). |
