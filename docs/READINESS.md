## Operational reporting design handoff

Current code stays synthetic-only. Before an operational input switch, record permitted data classes/purpose; approved endpoint/storage; named access roles; encryption/backup/restore; ORCON/PROPIN/PII/PII Red/FI inheritance; permitted export destinations/telemetry; retention start/duration/exceptions/deletion owner/verification; incident/stop route. Resolve conflicting vendor declarations rather than choosing 30 days by default. Real evidence and decision references belong in authorized storage, not this public repository.

Transition design must separate preparation/operational entrypoints and configuration; prohibit automatic cloud handoff; bound any future file/URL/attachment processing; require human report review/release; preserve lineage/markings and atomic output; render malicious text literally; and clean up exposed temporary files on failures. A human assertion string does not authenticate approval: the endpoint owner must select actual enforcement.

Before real-data support, approved-host synthetic checks must demonstrate denied unauthorized inputs/exports, restricted workspace permissions, no unintended transfer/telemetry, combined markings on every format, failed-render cleanup, revision/review preservation, authorized backup/restore and agreed retention/deletion. A separate implementation/review and applicable approvals are required; this handoff adds no bypass flag.

## Bounded runtime verification handoff

Use existing selected-tool [runbooks](../tooling/farmkit/RUNBOOKS.md), not general scanner defaults for OT. The owner selects only the required subset; no broad benchmark or previously excluded drill is commissioned here.

1. Record host/image digest, OS/architecture/Python/.NET/privileges, exact tool/dependency/template inventory and approved staging. Retain local offline metadata check output.
2. Name the isolated authorized lab, target allowlist/exclusions, protocol/unit/address/topic bounds, permitted read operation, timeout/retry/rate limits, expected result, stop condition and observer. Infer no controller writes, broadcasts or new targets.
3. Observe the selected operation and logs/PCAP in approved storage. Check success, partial response, refusal/timeout and operator stop. Record traffic/resources for this operation; claim no universal safe rate or participant speed gain.
4. Retain expected/actual result, exit/stage status, versions/hashes, evidence location, disruption/cleanup/retest and reviewer. Update only the corresponding existing readiness gate. Failed/not-run checks stay visible.
5. Verify Windows/.NET/payload destinations separately on approved hosts. No payload execution belongs to this local remediation. Corrected pristine install/recovery needs an authorized disposable host and complete result including failed steps.
