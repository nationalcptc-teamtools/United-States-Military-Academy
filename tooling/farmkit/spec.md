# Farming toolkit specification

Stable requirements for proposal `farm-toolkit`, v1.1.0, 2026-10-15. Original Analyst IDs remain unchanged. This public extract excludes private customer/planning context. All agriculture scenarios are hypotheses.

Baseline: config/Nmap orchestration and exports already exist; reporting PR #1 supplies the passive normalized-JSON reporter. The former installer used moving Vulscan and optional global pip. The desired result adds a researched catalog, integrity/readiness contracts and a separate easy assessment installer. No asset inventory or event-specific permission is available.

## Functional acceptance

| ID | Required outcome | Observable acceptance criterion |
| --- | --- | --- |
| FR-FT-001 | Maintain a useful, prioritized catalog | Every `TOOL-001` through `TOOL-040` has a recorded selected/conditional/lab/hold/excluded disposition and reason. LinPEAS and WinPEAS are present by name. Selected tools are distinguished from research candidates and alternatives. |
| FR-FT-002 | Make entries actionable and attributable | Each selected tool records canonical upstream, purpose, protocol/scenario, license source and status, runtime/architecture, dependency/privilege/hardware needs, operation class, output types, limits, maintainer, checked date and smoke-check reference. Unknowns remain explicit; there are no invented pins, approvals or compatibility claims. |
| FR-FT-003 | Cover flexible primary OT interfaces | A matrix maps Modbus TCP/RTU, Siemens S7, EtherNet/IP CIP, OPC UA, BACnet/IP, MQTT and passive packet inspection to at least one candidate each. Serial-only variants name adapter constraints. Protocol/vendor coverage is supported by upstream evidence and is never inferred from a port alone. |
| FR-FT-004 | Cover agriculture-specific possibilities without inventing scope | Explicitly address CAN/J1939/ISOBUS, CANopen, LoRaWAN, Zigbee, MAVLink, DNP3, IEC 60870-5-104, IEC 61850 and DLMS/COSEM as conditional coverage, lab-only options or documented gaps. CAN decoding does not imply complete ISOBUS/implement support; energy protocols do not imply the customer operates a utility. |
| FR-FT-005 | Support Linux and Windows host assessment | A synthetic Linux and Windows evaluation path exists for selected host-enumeration tools. Document execution prerequisites, resource/AV effects and sensitive output handling. Failure to run under restricted privileges or endpoint protection is reported; it must not become “no escalation paths.” No automatic exploit step follows enumeration. |
| FR-FT-006 | Select and acquire reproducibly | Each staged artifact has an exact source commit/release, download/build provenance, architecture and SHA-256; dependencies and required data files are pinned or included in an identified distro snapshot. No `latest`/moving-branch-only manifest qualifies. Modified upstream files and source/license obligations are tracked. Tampered or missing artifacts fail verification before use. |
| FR-FT-007 | Separate preparation from operational behavior | Acquisition/installation performs no discovery or target activity. Default checks use local synthetic files or an isolated lab. Active profiles require explicit authorized target, protocol and operation; missing scope cannot fall back to scanning a subnet. Unlimited polling, automatic broadcast discovery, broad defaults and writes are absent from team-provided default profiles. |
| FR-FT-008 | Provide bounded OT runbooks | Selected active operations state exact request type, possible side effects, request/connection budget, timeout, retry policy, destination/unit/address range, required credentials, stop conditions, evidence fields and cleanup. Reads are labeled active; MQTT subscriptions and protocol handshakes are not labeled passive. Any unexpected controller behavior stops the activity and routes to the engagement lead/incident process. |
| FR-FT-009 | Preserve evidence and report boundaries | Example records capture tool/version, profile, operator, timestamps/timezone, approved scope reference, exit/partial status, evidence ID/hash and limitations using synthetic data. Unsupported protocol, timeout, authentication error and empty results remain distinct. Raw output is private by default. A reporting handoff may use the existing normalized contract; adapters or automatic finding confirmation are not implied. |
| FR-FT-010 | Exercise representative lab paths | Rehearsal demonstrates offline PCAP interpretation plus a controlled read/query for each selected primary protocol family using synthetic fixtures/simulators. Network capture or equivalent observation verifies the team-provided profile's allowed traffic and lack of writes. Unavailable hardware/protocols are marked not run with the resulting acceptance gap. |
| FR-FT-011 | Prepare reviewable repository integration | A later integration plan records fresh repository revision/conventions, eligible student owner, license notices, selected artifact locations and ignored private outputs. Existing scanner/reporting behavior remains separate unless an explicit mapped change is designed. No existing file is silently replaced. Repository access and approval are recorded before an eligible maintainer publishes. |
| FR-FT-012 | Preserve competition readiness evidence | A readiness record identifies applicable rules/SOW/ROE, actual event start/timezone, repository assignment, eligible maintainers, staging decision, frozen version/hash and outstanding exceptions. Calculate request/freeze deadlines only from the confirmed event start and any stricter official deadline. The historical README date and November development milestone cannot supply that timestamp. |

## Quality acceptance

| ID | Constraint | Observable acceptance criterion |
| --- | --- | --- |
| NFR-FT-001 | Truthful evidence and scope | Every customer-specific statement is sourced or marked hypothesis. Candidate capability, upstream declaration, local test, independent review, user acceptance and event approval are separately recorded. A library supporting reads/writes is never called intrinsically read-only. |
| NFR-FT-002 | License fidelity | Every selected artifact retains its actual license/notice and required source information. Repository MIT licensing is not applied to third-party components. PEASS custom GPL wording, BACpypes3 conflicting declarations, mixed-license components and modified licenses remain explicit holds until a documented maintainer review resolves the intended use/distribution. No OSI-certification claim is inferred from a GitHub badge. |
| NFR-FT-003 | Reliable offline operation | On the agreed clean Kali/runtime image, selected tool help/version and applicable synthetic smoke checks pass with Internet egress blocked. No account, paid API, remote fallback or automatic update is needed. Missing dependencies fail clearly; cached packages on a developer machine are not proof. Record preparation time, disk/RAM needs and installation privileges before accepting the package. |
| NFR-FT-004 | Availability and bounded load | Default OT profiles avoid fan-out, endless retries and uncontrolled discovery; every active profile has measured lab bounds and a stop path. No universal “safe packet rate” is claimed. OT profiles do not inherit the existing wrapper's `-T4`, all-port or broad-script choices. |
| NFR-FT-005 | Data minimization | Public artifacts contain only code, notices, synthetic fixtures and generic examples. No client captures, names beyond already authorized proposal context, credentials, host inventories, production registers or derived findings are committed. Output locations are explicit and outside tracked/synced source areas during engagements; ignore rules are not treated as an upload control. |
| NFR-FT-006 | Maintenance and substitution | Every selected release has a dated maintenance/security review with known limitations, dependency issues and replacement/fallback decision. Archived/inactive projects are conspicuous; they cannot silently enter the default kit. An unreviewed update requires new provenance and affected smoke checks. |
| NFR-FT-007 | Navigable and verifiable handoff | Local links resolve, requirement/tool IDs are unique, every requirement maps to a design element and later verification method, and instructions distinguish CLI tools, developer libraries and lab servers. A student competitor can identify an applicable tool and its prerequisites/limits from the catalog. Independent review is recorded before substantial implementation is accepted. |

All forty candidates have automated/optional/manual/held dispositions. No silent failure, unverified payload replacement, global pip or automatic tool/server execution. Installation inventory records actual resolved versions and pins separately from operational readiness. |

## Boundaries, evidence and remaining decisions

Canonical evidence appears per tool in [CATALOG.md](CATALOG.md), source/asset evidence in [sources.json](sources.json) and [install-manifest.json](install-manifest.json), actual results in [VERIFICATION.md](VERIFICATION.md). The [October 2025 rules](https://cp.tc/docs/cptc-rules.pdf) are the requested working rulebook baseline. Current package candidates are researched in October 2026; historical availability in October 2025 is not asserted.

Preserved decisions: OD-FT-01 actual event/start/timezone/SOW; OD-FT-02 assigned repository/eligible student owner/frozen revision (publication authorized, event approval separate); OD-FT-03 exact team OS/Windows/.NET/resources; OD-FT-04 permitted acquisition/staging/snapshots; OD-FT-05 artifact/dependency/license and output-integration review; OD-FT-06 actual in-scope protocols and allowed reads; OD-FT-07 lab/hardware/rehearsal owner; OD-FT-08 provisional eight core routes, package budget and future adapter funding. Captain/runtime/license owners must resolve their respective gates. The reporting base's historical README says NLT 16OCT; refreshed master c2468f2 says 19 October and adds consolidated Linux/Windows runners. Neither text supplies the actual event/start/timezone. Confirm the applicable official cutoff rather than deriving event dates from either note.

Reversible assumptions: Kali x86-64 plus separate Windows x64 payload destination; offline operation after online acquisition; broad protocol candidates rather than all forty auto-installed; only synthetic preparation data. No real-farm reconnaissance, controller writes/logic/firmware/start-stop, injection/RF, credential attacks or operational testing is included. Legacy scanner timing/exit/parsing defects are static observations and remain separate work. Setup does not repair scanner behavior.

Missing scope means no target activity. Missing artifacts, changed bytes, failed dependencies, redirected paths, wrong source commits and command failures must fail explicitly. Partial/timeout/authentication/unsupported/empty outcomes remain distinct. No hardware means not run, never inferred compatible. Full FR-FT-006 offline dependency closure and FR-FT-005/010 operational rehearsals remain acceptance gaps despite successful software installation. See [design](design.md) for mappings and [runbooks](RUNBOOKS.md) for bounded operations.
